# YogaTutor 暑假进展汇报详细解说稿

建议时长：约 10 分钟  
使用版本：`outputs/YogaTutor_暑假进展汇报_完整.pptx`

## 第 1 页 封面

各位老师好，我今天汇报的项目是 YogaTutor，题目是“基于视觉感知和单腕触觉引导的实时动作矫正系统”。

这个项目面向瑜伽练习场景。我们希望系统不仅能判断用户的动作是否标准，还能进一步告诉用户应该往哪个方向调整。这里的核心思路可以概括为两点：第一，用摄像头识别人体姿态，找出动作偏差；第二，用手环震动把纠正方向反馈给用户。

本次汇报主要介绍我在暑假期间完成的阶段性工作。重点不是单独讲某一个算法，而是讲系统如何从前期的姿态识别和标准姿势库，推进到一个可以演示的网页 MVP。

## 第 2 页 项目目标：让用户看见偏差，感受调整方向

这一页讲项目为什么要做。

在普通瑜伽练习中，用户通常只能对照视频或图片练习。问题是，用户很难实时判断自己到底哪里不标准，比如手臂有没有抬够、膝盖弯曲角度是否合适、髋部是否打开到位。

如果只依赖屏幕提示，练习者还需要低头看屏幕，这会打断动作保持。尤其是像 Warrior II 这种需要身体稳定展开的动作，频繁看屏幕本身就会影响练习效果。

所以 YogaTutor 的目标不是只给一个分数，而是建立一个练习闭环：摄像头负责观察动作，系统负责计算偏差，手环负责把调整方向反馈到身体上。这样用户在保持姿势的同时，就能通过触觉知道下一步应该怎么调整。

## 第 3 页 暑假工作总览：从主程序到可演示网页 MVP

这一页是暑假工作的整体时间线。

前期项目已经有标准姿势库和一些基础算法模块。暑假阶段的重点，是把这些分散的模块整合成一个能跑通、能展示、能连接硬件的系统闭环。

7 月主要完成了统一主程序的整合。系统支持自动识别模式和手动选择模式，并把姿态检测、滤波、静止检测、评分和触觉反馈放进同一条流程里。

随后完成了 ESP32 手环固件和串口通信协议。PC 端可以通过 USB 串口向 ESP32 发送马达指令，ESP32 再控制左手环的不同方向震动。

8 月的重点是网页 MVP。网页端固定使用 Warrior II Pose 作为目标姿势，浏览器负责摄像头采集和界面展示，本机 Python 服务负责识别、评分和手环控制。

同时也做了闭环稳定性增强，比如串口保活、无硬件模式、自动停震保护，以及后续 BLE 蓝牙迁移方案。这里需要强调，BLE 目前是迁移方案，不是已经完成的功能。

## 第 4 页 系统架构：视觉、评分和触觉反馈形成闭环

这一页讲系统整体架构，但只讲主线。

整个流程从摄像头帧开始。摄像头画面进入系统后，首先由 MediaPipe 提取人体关键点。接着用 1€ Filter 对关键点做平滑处理，减少画面抖动带来的角度波动。

然后系统会进行静止检测。只有当用户保持姿势稳定一段时间后，系统才开始正式评分。这样可以避免用户还在移动时就给出不准确反馈。

评分阶段会计算 8 个关键关节角，包括左右肘、左右膝、左右肩和左右髋。系统将这些角度与标准姿势中的角度进行比较，得到当前得分和各关节偏差。

最后，触觉映射模块会把偏差转换成手环马达指令，通过 ESP32 控制左手环震动。也就是说，系统不是停留在“识别结果显示在屏幕上”，而是把结果进一步转化成身体可以感受到的反馈。

## 第 5 页 姿态感知：从 33 个关键点提取 8 个关节角

这一页简单说明视觉部分。

系统使用 MediaPipe Pose 检测人体姿态。MediaPipe 会输出 33 个身体关键点，比如肩、肘、手腕、髋、膝和脚踝。

在我们的评分任务中，不需要使用全部关键点，而是重点选择与瑜伽姿态相关的核心关节。当前系统主要计算 8 个关节角，也就是左右肘、左右膝、左右肩和左右髋。

这 8 个角度可以比较好地描述 Warrior II 这类动作的主要姿态特征。例如手臂是否水平展开、前腿膝盖是否弯曲、身体髋部是否打开，都可以通过这些角度反映出来。

另外，系统设置了检测和跟踪置信度阈值，并加入静止检测。这样做的目的，是让识别结果更稳定，也让后续评分和触觉反馈更可靠。

## 第 6 页 标准姿势库：前期基础支撑假期 MVP 演示

这一页介绍标准姿势库。

项目中已经建立了标准姿势数据。标准姿势来自图片，每张标准图经过姿态提取后，会保存为 JSON 文件。JSON 中包含人体关键点、图像尺寸、姿势名称，以及平均关节角。

目前项目中已有 18 个标准姿势 JSON，包括 Warrior I、Warrior II、Tree、Triangle、Plank、Wheel 等动作。这些数据为后续动作识别和姿态评分提供了基础。

在网页 MVP 阶段，我们没有一开始就把所有动作都接入网页，而是选择 Warrior II Pose 作为固定目标。这样可以减少变量，先把浏览器、Python 服务、评分逻辑和手环反馈这条链路跑通。

后续扩展时，可以在网页端加入动作选择，让用户从标准姿势库中选择不同目标动作，再调用同一套评分和反馈流程。

## 第 7 页 网页 MVP：采用 B/S 本地架构

这一页是第四部分的重点，从这里开始讲网页 MVP。

当前网页采用的是 B/S 本地架构。这里的 B 指 Browser，也就是浏览器客户端；S 指 Server，也就是本机 Python 服务。

浏览器客户端主要负责三件事：第一，调用电脑摄像头采集画面；第二，展示网页界面，包括目标姿势、评分、关节偏差和手环状态；第三，处理用户点击，比如开启摄像头和重新评估。

中间是 HTTP 本地接口。网页会调用 `/api/status` 获取服务状态，调用 `/api/frame` 上传摄像头帧，调用 `/api/reset` 重置当前评估。

Python Server 运行在同一台电脑上。它收到浏览器发来的 JPEG 摄像头帧后，运行 MediaPipe，计算关键点和关节角，然后完成静止检测、评分和触觉指令生成。

最后是 ESP32 手环。Python 服务通过 USB 串口把方向和强度指令发给 ESP32，ESP32 再控制左手环马达震动。

这里要特别说明一个容易混淆的点：当前网页传输的是 JPEG 摄像头帧，不是浏览器端已经计算好的肢体点阵。也就是说，关键点计算发生在本机 Python Server 中，而不是浏览器前端。

如果后续要让手机或其他电脑访问这个系统，可以把电脑作为局域网服务器。但那时涉及摄像头画面或人体关键点数据传输，就应该使用 HTTPS 或 WSS 来保护数据。

## 第 8 页 本机服务器负责计算，浏览器负责采集和展示

这一页进一步拆开网页的数据流。

第一步是采集。浏览器通过摄像头权限获取视频画面，并按一定间隔从视频中截取帧，生成 JPEG 数据。

第二步是传输。浏览器把这一帧通过 HTTP POST 请求发送到本机的 `/api/frame` 接口。这里的服务器地址是 localhost，所以当前演示是在同一台电脑内部完成的。

第三步是计算。Python 服务收到图像后，使用 MediaPipe 检测人体关键点。如果关键点不完整，系统会提示用户后退或调整位置，确保肩、手腕、髋、膝和脚踝都在画面内。

如果人体关键点完整，系统会继续进行滤波和静止检测。用户保持 Warrior II 姿势稳定后，系统才计算关节角并与标准姿势比较。

第四步是反馈。服务器返回评分、关节偏差和提示信息，网页负责把结果显示出来。同时，如果有需要纠正的动作，服务器会生成手环指令并发送给 ESP32。

采用本机服务器的好处是延迟低、部署简单，而且摄像头画面不需要上传到公网。对于当前这种需要连接 USB 手环的 MVP，本机服务也更方便控制硬件。

## 第 9 页 网页界面：一页完成练习、评分和手环状态展示

这一页展示网页界面。

页面左侧是实时练习工作台。用户点击“开启摄像头”后，浏览器会显示摄像头画面，并在画面上叠加姿态检测结果。当前截图中显示的是未开启摄像头状态，真实演示时这里会显示用户身体画面和姿态骨架。

右侧上方是目标姿势区域。当前 MVP 固定选择 Warrior II Pose，并显示标准姿势参考图。用户可以直观看到系统以哪一个标准动作作为比较对象。

右侧下方是当前评分区域。系统在用户稳定保持动作后，会更新当前分数，并显示是否正在等待摄像头、静止检测中，还是正在评估。

页面右侧还包含关节偏差列表。这里会列出每个关节的当前角度、标准角度和偏差，让用户知道具体是哪个部位出现了问题。

下方的左手环引导模块展示触觉反馈状态，包括 USB 是否连接、当前震动方向，以及对应的马达方向。这样网页不仅是一个摄像头界面，也是整个系统闭环的状态面板。

## 第 10 页 触觉反馈：把最大角度偏差转成一个震动方向

这一页讲触觉反馈逻辑。

当前 MVP 使用的是已经验证过方向的左手环。每个手环有四个方向的马达，分别对应上、下、左、右。

系统并不会同时把所有偏差都发给手环，因为这样用户可能很难理解多个震动代表什么。当前策略是选择优先级最高的一个偏差，也就是相对于阈值来说最严重的关节偏差。

举例来说，如果左肘和右膝都有偏差，系统会先比较它们的偏差程度和各自阈值的比例，然后选择最需要纠正的那个关节。

确定关节后，系统会根据关节类型和偏差方向映射到手环马达。当前方向映射是：上对应 M2，下对应 M0，左对应 M1，右对应 M3。

强度也不是固定值，而是根据偏差程度分级。偏差越大，震动强度越高。当前使用的强度等级包括 150、200 和 255。

这一页可以重点强调：手环不是简单的提醒装置，而是在承担方向引导的角色。用户不需要一直看屏幕，也能通过手腕上的震动感知调整方向。

## 第 11 页 硬件通信：USB 串口闭环和停震保护

这一页讲硬件通信和安全机制。

当前 PC 到 ESP32 的通信使用 USB 串口，波特率是 115200。Python 服务生成字符串指令，然后通过串口发送给 ESP32。

页面中展示的示例指令是 `L:2,150 R:N`。它的含义是：左手环的 2 号马达以 150 强度震动，右手环没有动作。

这里虽然协议里保留了左手环和右手环两个字段，但当前实物验证重点是左手环。也就是说，协议设计预留了扩展空间，但演示时不要把右手环说成已经完成。

为了安全，系统加入了停震保护。电脑端会定期发送保活命令，间隔是 0.75 秒。如果 ESP32 固件 2 秒没有收到新的有效命令，就会自动关闭所有马达，避免因为程序异常导致马达持续震动。

此外，系统也支持无硬件模式。如果没有连接 ESP32，视觉识别和网页展示仍然可以运行，只是不会输出触觉反馈。这样调试网页和算法时不会被硬件连接状态卡住。

BLE 蓝牙迁移目前已经有方案，包括用 BLE GATT Service 保留现有上层指令格式。但这一部分仍属于下一阶段计划，当前汇报中应明确说成“已规划”，不要说成“已完成”。

## 第 12 页 总结与下一步

最后总结一下本次暑假进展。

暑假阶段的核心成果，是把 YogaTutor 从分散的算法和硬件模块推进到了一个可以演示的本地 MVP。系统已经能够通过浏览器采集画面，由本机 Python 服务完成姿态识别和评分，并通过 USB 串口控制 ESP32 左手环进行方向提示。

从功能上看，当前已经跑通了 Warrior II 的练习闭环。用户可以在网页中看到目标姿势、当前评分、关节偏差和手环引导状态。这个结果说明系统已经具备从视觉识别到触觉反馈的完整链路。

下一阶段主要有四个方向。

第一，把 USB 串口迁移到 BLE 蓝牙，让手环摆脱线缆限制，更接近真实使用场景。

第二，扩展双手环。当前协议已经保留左右手字段，但实物和固件还需要进一步确认 GPIO 分配和方向映射。

第三，网页端支持更多标准姿势选择。现在网页 MVP 固定 Warrior II，后续可以接入已有的 18 个标准姿势库。

第四，补充真实用户测试和长期稳定性验证。重点观察识别稳定性、评分合理性、触觉提示是否容易理解，以及手环长时间运行是否可靠。

整体来说，这个暑假完成的不是单点功能，而是把“视觉识别、姿态评分、网页交互、硬件触觉反馈”连成了一个边界清晰的演示系统。后续工作会围绕无线化、多动作和用户测试继续推进。

## 备用问答

### 1. 为什么网页端不直接计算人体关键点？

当前选择 Python Server 计算，主要是因为项目原有算法模块都在 Python 中，包括 MediaPipe、姿态比较、静止检测和手环控制。这样可以最快复用已有代码，并且方便连接 USB 串口手环。后续如果要降低服务端压力，也可以考虑把关键点检测迁移到浏览器端。

### 2. 当前传输的是视频流还是关键点？

当前传输的是 JPEG 摄像头帧。浏览器按帧发送图片到本机 `/api/frame`，服务器再计算关键点和评分。严格来说不是连续视频流，也不是已经计算好的肢体点阵。

### 3. 为什么只做 Warrior II？

Warrior II 的姿态特征清晰，手臂、膝盖和髋部角度都适合展示评分和纠错。暑假阶段先固定一个动作，可以减少变量，重点验证网页、算法和手环能否形成闭环。

### 4. BLE 是否已经完成？

还没有。BLE 目前是迁移方案。当前完成的是 USB 串口 MVP，已经能进行本机网页演示和左手环方向反馈。BLE 会作为下一阶段扩展。

### 5. 没有手环时系统还能运行吗？

可以。系统有无硬件模式或静默降级逻辑，没有 ESP32 时仍然可以运行视觉识别和网页展示，只是不会发送震动反馈。
